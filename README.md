# RazorPay Pulse — AI Payment Experience Intelligence

**Category:** 02 — AI Risk Manager
**Status:** ✅ Deployed and live on Google Cloud (Cloud Run + BigQuery + Vertex AI)

Existing payment systems answer *"was the payment successful?"* RazorPay Pulse answers *"why did the payment experience degrade, who's affected, what's likely to happen next, and what should we do about it?"*

Core loop: **Detect → Explain → Predict → Recommend.**

This is not a payment gateway, not a routing engine, and not a chatbot — it's an AI-powered risk intelligence console for payment ops/risk teams, built as a real full-stack SaaS product.

## What's implemented

- ✅ FastAPI backend with a repository-pattern data layer — **`BigQueryStore` is live**, writing every transaction, incident, prediction, and recommendation into BigQuery in real time
- ✅ Payment traffic simulator generating realistic transactions across the full Payment Journey (checkout → order API → gateway → payment method → bank → callback)
- ✅ Judge-facing simulator injection endpoints (latency, failure rate, per-method/region targeting)
- ✅ Metrics engine: success rate, P95/P99 latency, value-at-risk, health status, computed live from BigQuery
- ✅ Rule-based anomaly detection → automatic incident creation, tuned to fire within ~30–60s of an injection
- ✅ Lightweight predictive risk (trend extrapolation, not a heavyweight ML model — matches the brief)
- ✅ **AI root-cause analysis via real Gemini (Vertex AI)** — aggregated telemetry only, never raw transaction rows, validated against a strict JSON schema before display
- ✅ Advisory recommendation engine tied to incidents
- ✅ Full Next.js/TypeScript/Tailwind frontend: Overview dashboard, Live Transaction Monitor with filters, Payment Journey drill-down, AI Incident Center, Predictions, AI Recommendations, and the Simulator control panel
- ✅ Docker + docker-compose for one-command local run
- ✅ BigQuery DDL (`BIGQUERY_SCHEMA.sql`) — deployed and live in the `razorpay_pulse` dataset
- ✅ Deployed end-to-end on Google Cloud Run (frontend + backend), authenticated to BigQuery and Vertex AI via the Cloud Run service account (no hardcoded credentials anywhere in the codebase)

## What's still simulated / not wired

- **Razorpay Test/Sandbox integration** — the app currently runs entirely on simulated traffic. Real Razorpay test-mode transactions are not yet flowing in; the `source` field on every transaction is tagged `"simulated"` for exactly this reason. Wiring this up is the main remaining gap.
- **Pub/Sub async ingestion** — traffic is generated by an in-process loop inside the backend rather than published to Pub/Sub and consumed separately. This is the correct shape for a demo; a production version would decouple ingestion this way instead.
- **Cloud Monitoring** — not wired up. Optional per the brief, and not required for the core demo loop.

## Demo script

1. Open the **frontend URL** — Overview shows a healthy baseline (P95 ~450–600ms, success rate ~97–100%), live from BigQuery.
2. Go to **Simulator** → trigger **"Bank delay — UPI"** (injects 4000ms bank-stage latency for UPI).
3. Watch **Overview** — P95/P99 rise, health flips to DEGRADED/CRITICAL within ~30–60 seconds.
4. Open **Incidents** — a new incident has been auto-created (severity, affected transactions, value at risk).
5. Open the incident → click **"Run analysis"** → aggregated telemetry is sent to **Gemini via Vertex AI** → root cause, confidence, affected segment, and a recommendation come back and are shown.
6. Check **AI Recommendations** — advisory actions generated from the incident (surface alternate payment method, escalate, monitor region).
7. Check **Predictions** — trend-based forecast for UPI shows elevated degradation probability.
8. Click **"Reset simulator"** on the Simulator page — traffic returns to baseline; watch the Overview latency chart recover.

## Running it yourself

### Against the live deployment
Just open `https://razorpay-pulse-frontend-212225425691.us-central1.run.app/` — nothing to install.

### Locally (mock mode, no GCP needed)

```bash
docker compose up --build
```
- Backend: http://localhost:8080 · Frontend: http://localhost:3000

Local runs default to `DATA_BACKEND=memory` and `AI_PROVIDER=mock` via `backend/.env.example`, so you don't need GCP credentials just to develop against it. See `backend/.env.example` for every flag.

### Locally against your live BigQuery + Vertex AI

```bash
gcloud auth application-default login
cd backend
cp .env.example .env
# edit .env: DATA_BACKEND=bigquery, AI_PROVIDER=vertex, GCP_PROJECT_ID=<your project>
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8080
```

## Redeploying to Google Cloud

The app is already deployed; use this if you change code and need to push an update.

```bash
gcloud config set project <PASTE_PROJECT_ID>

# Backend
cd backend
gcloud run deploy razorpay-pulse-backend \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --set-env-vars DATA_BACKEND=bigquery,GCP_PROJECT_ID=<PASTE_PROJECT_ID>,AI_PROVIDER=vertex,FRONTEND_ORIGIN=<PASTE_FRONTEND_URL>
cd ..

# Frontend (only needs redeploying if backend URL changes or frontend code changes)
cd frontend
gcloud run deploy razorpay-pulse-frontend \
  --source . \
  --region us-central1 \
  --allow-unauthenticated \
  --set-build-env-vars NEXT_PUBLIC_API_BASE_URL=<PASTE_BACKEND_URL>
cd ..
```

### IAM (already granted for the live deployment, kept here for reference)

```bash
PROJECT_NUMBER=$(gcloud projects describe <PASTE_PROJECT_ID> --format="value(projectNumber)")

gcloud projects add-iam-policy-binding <PASTE_PROJECT_ID> \

  --member="serviceAccount:${PROJECT_NUMBER}-compute@developer.gserviceaccount.com" \
```

### Notes

- No API keys or credentials are hardcoded anywhere in this codebase — Cloud Run's service account authenticates to BigQuery and Vertex AI via the IAM roles above.
- `--allow-unauthenticated` is used for demo simplicity. For anything beyond a buildathon demo, remove it and put Cloud Run behind IAM-based access control or an API gateway.
- Each `gcloud run deploy --source .` re-runs Cloud Build, so a redeploy after any code or env-var change takes a few minutes.

## Adding real Razorpay Test/Sandbox data (the one remaining gap)

Currently every transaction is simulated. To layer in real Razorpay test-mode transactions alongside the simulator:

1. Get your Razorpay **Test Mode** key ID/secret from the Razorpay dashboard.
2. Uncomment `razorpay==1.4.2` in `backend/requirements.txt`.
3. Set `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` in `backend/.env` (never commit real secrets — `.env` is gitignored).
4. Add a small ingestion path that pulls test-mode payments via the Razorpay SDK, maps them into the `Transaction` schema with `source="razorpay_test"`, and calls `store.add_transaction()` — the rest of the pipeline (metrics, anomaly detection, AI analysis) already works on any transaction regardless of source.
5. The UI already distinguishes sources — `source` is exposed on every transaction so simulated and real data are never confused, per the brief's requirement.

## Design notes

The frontend follows an enterprise-observability visual language (dark graphite base, indigo reserved specifically for AI-generated content so it's visually distinct from raw telemetry, standard green/amber/red severity signaling). The product's "Pulse" name is reflected literally: the `PulseLine` component isn't just a logo mark — the same heartbeat-trace element is reused as the Payment Journey connector, where the spike height is driven by that stage's real latency rather than being decorative.
